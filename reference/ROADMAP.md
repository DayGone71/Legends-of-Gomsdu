# Roadmap

Legend: **\[Ready\]** clear enough to build directly. **\[Discuss\]** flagged as needing a live conversation before building. **\[Resolved\]** clarified, folded into the plan below. **\[Deferred\]** discussed and intentionally punted into a different, larger item rather than resolved here.

**Build-order note (added 2026-08-15):** the section order below is *not* the real dependency order. Control mechanics under **Stats** (Control-substitution, Life, Control tiers) are logically upstream of both **Party System** and **Movement System** — Free-Will/Possessed, the mini-DM Control mechanic, and how multiple party members move/act together all depend on Stats being settled first. Real build order: **Stats → Movement → Party**, not the top-to-bottom document order. Party System and Movement were deliberately skipped in this session's pass for exactly this reason.

-   **H \[Resolved, built\]** **The Ally Targeting System — built and verified 2026-08-16.** dDd's own framing: a springboard feature, three near-identical interface changes across Combat/DM/DM Test that all needed the same underlying fix — before this, a Player could only ever target `table.enemies` and an Enemy could only ever target `table.players`, so "which collection is this id in" was always inferable from who was attacking. That invariant broke the moment a Player needed to target an ally. New shared resolution layer in [js/utils.js](../js/utils.js): `resolveEntityRef(table, targetId)` resolves any id — a plain Player/Enemy id, or a composite `'mp:<playerId>:<index>'` id for a **statted** Mini-Party member (one added with a base build, so it actually has `wounds`/`woundsMax` to track; un-statted stubs are skipped everywhere, nothing to track) — regardless of which collection it actually lives in; `ownerTypeOf()` derives the real Block-registry owner side from where the target resolved, not from who attacked; `possessedEnemyIds()`/`alliedActorIds()` compute, respectively, which live Enemies are currently someone's Possessed Mini-Party member (ally now, not hostile) and the full ally-side id list (every Player + every statted/Possessed Mini-Party member). `resolveRound()` in [js/combat.js](../js/combat.js) now gathers staged sequences from statted Mini-Party members too (as `'player'`-side actors under their composite id), and runs them through the *exact* same end-of-round Recovery/Attunement tick and sequence/apSpent reset as real Players/Enemies — they're full actors now, not just targets. The three concrete changes:
    -   **Combat Panel: new "Ally Range."** Mirrors Target Range exactly (`#ally-range` in [index.html](../index.html), `renderAllyRange()`/`selectAllyTarget()` in combat.js) — the Player, every other Player at the table, and their statted Mini-Party members, each targetable by Attack/Block/Essence the same way an Enemy is (matches the existing "anybody can Technique/target anybody, for Testing purposes" precedent already set for Techniques). A Possessed Enemy now shows up here instead of on Target Range — it's an ally, so `renderTargetRange()` excludes anything in `possessedEnemyIds()`. Selection is unified into one `AppState.selectedTargetId` + new `selectedTargetSide` ('enemy'/'ally') rather than two independent fields, so only one chip across both ranges is ever highlighted. Verified live: staged a Fast Attack on a statted Mini-Party member ("Rex," a Stray-Dog-build Mini-Party stub) through the real UI, resolved it, confirmed real Wound/Down/Flow-overwhelm math applied to the *nested* `player.miniParty[i]` object correctly — then attacked Rex again while Down and confirmed Execution triggers against an ally exactly like it does against an Enemy, no special-casing needed since both paths now go through the same `resolveEntityRef`.
    -   **DM Panel: reordered + Acting As self-targeting.** Per dDd's two stacked instructions (move Target-Players under Acting-As, and separately swap Acting-As with the Stat Breakdown), the panel now reads **Stat Breakdown → Acting As → Target (players)** top to bottom (was Acting As → Stat Breakdown → Target). Double-clicking the Acting As chip (`toggleActingSelfTarget()` in [js/dm.js](../js/dm.js)) toggles that Enemy as its own target — a second double-click clears it — rendered with a distinct green `.self-targeted` ring (reusing the same green established for Ally-crowding on the Map, per [style-guide.md](style-guide.md)'s "reuse established hues" rule) alongside the existing brass "currently acting as" highlight. Switching which Enemy you're Acting As drops a stale self-target rather than silently carrying it to the new one. Verified live: double-click correctly toggled the visual state, staged a self-targeted Fast Attack, and resolving it correctly logged the Enemy attacking itself (in this case, Executing itself into Obliteration, since it happened to already be Down from an earlier round — a genuine, mechanically-correct edge case, not a bug).
    -   **DM Test Panel: "Players" now includes Mini-Party + allied Players.** `renderDMTestPanel()`/`runOneRound()` in [js/dmtest.js](../js/dmtest.js) both switched from iterating `table.players` directly to `alliedActorIds()`, so every statted Mini-Party member and every Possessed Enemy gets its own auto-battle row (target dropdown + Fast/Strong/Hold) alongside each real Player; the "Enemies" side excludes Possessed ones the same way Combat's Target Range does. `runRoundsLoop()`'s win-condition checks now use ally-aware/Possession-aware counts (`countAliveAllies`/`countAliveEnemies`) instead of raw collection counts. Verified per dDd's own suggested method — opened a genuine second browser tab, joined the same table code as a second Player ("Ally2"), and confirmed in real time that both the first tab's Ally Range *and* the DM Test Players list picked up the new Player and its own row without a reload, alongside the already-present Mini-Party member.
    -   **Known-wrong-on-purpose, not yet fixed: General Block currently works between Allies.** Because Block-matching now derives its owner side from where the target actually lives (`ownerTypeOf`) rather than from who's attacking, an ally's staged Block technically intercepts a friendly-fire hit today — which is code-consistent but narratively backwards. See item I below.
-   **I \[Discuss\]** (added 2026-08-16) **Betrayal Attack + Hara Kiri** — two mechanics dDd designed live, watching item H's Block-between-Allies edge case unfold, specifically because a plain boolean ("is this Ally-on-Ally") turns out to carry real narrative weight (his example: a powerful Character's close friend lands a Betrayal Wound on them from the same Tile). Neither built yet, both `[Discuss]`, but well-specified enough to pick up directly once queued:
    -   **Betrayal Attack**: attacking an Ally should never be "normal combat with the usual defenses" — General Block should **not** be able to intercept it at all (the item-H behavior above is the bug this fixes), and the hit itself should bypass Flow entirely with a very high (dDd's example: 99%) Hit%, the same shape Wound/Execution already use for "sometimes an attack skips the normal shield for a specific reason." The one exception: a Technique that *helps* rather than hurts its Ally target (Embolden/Anchor, a future heal) is obviously not a Betrayal — needs some notion of "is this Technique beneficial or harmful," which doesn't exist as an explicit flag on `TECHNIQUES` yet.
    -   **Hara Kiri**: self-targeting (Combat Panel's Ally Range now lets a Player target themselves; the DM Panel's Acting-As double-click already lets an Enemy do the same) as a deliberate, narratively-loaded act rather than an edge case to route around — dDd's framing: "oh no, Torso is now False and Wounds X = Wounds Y!" — instant jump to the personal Down threshold plus a real per-Character Chunk flipping false. Blocked on the same per-Character 6-Chunk array already queued as a Character Templates prerequisite (see Party System item C).

Design conversation, 2026-08-16, no code yet. Fuller design space, run past

-   **\[Resolved, foundational\]** **Combat is ~30% of the experience, not the core.** The other ~70% is World/Lore — "peaceful RPG" content built with the same "simple and deep" mechanical philosophy as Combat, not just flavor text. Solo CRPG play is explicitly "super important" — core, not optional. DM-run play (this build's actual origin — a DnD homebrew session) is "the skeleton," not the only mode. Named influences: **KOTOR** for the experience, **Kenshi** for Progression.
-   **\[Resolved, foundational\]** **The game's founding design pillars, restated directly by dDd: "Power Asymmetry and access to Information. It's always been Social, as far as the Design."** Every system downstream of this (Dialogue included) should read as an expression of that pillar, not a bolted-on feature.
-   **\[Resolved, foundational\]** **Not "OC as DM."** The story isn't Claude improvising live as a game master. Instead the game is heavily **scripted via Interactions** — clicking a Character on the Map, visiting a Town, any Dialogue Encounter — as the primary mechanism that drives the story forward, pivotal-moment by pivotal-moment. Architecturally, Interactions likely reuse the same data-driven, tagged-entry pattern already proven three times tonight (Techniques, Possessor slots, and now Dialogue Pools below) — not a new architecture, an extension of the established one.
-   **\[Resolved, foundational\]** **Dialogue content is pre-authored, not runtime-generated — "primarily, like Tier 5 Possessions": foundational and ever-present, not invented on the fly.** Each NPC/Faction holds a fixed **information pool** (facts, topics, reactions), authored **offline by OC** during normal chat/design conversations like this one, then stored as static game data. How a pool's content actually gets *rendered* to the Player varies by the NPC's **Personality**.
-   **\[Resolved, foundational\]** **Runtime resolution is AI, not OC — no live API call during play.** OC's role is strictly authoring-time (writing pool content in chat, ahead of time). At runtime, plain deterministic client-side logic (matching/filtering, same spirit as the Technique engine) selects what to surface from the pool. This is a refinement of the existing AI/OC naming split worth keeping in mind everywhere else that split gets used.
-   **\[Resolved, design\]** **The Player's side of Dialogue is not a tree, not a wheel, and not free text.** Trees and wheels were both rejected as "basically the same thing" (a single linear branching choice); free text was rejected as too random to match deterministically without real NLU/a live API call. Instead the Player expresses their approach via independent, selectable **Axes** — dDd's own term, adopted as the working name — e.g. **Tone, Language (complex/simple, knowledge of local customs), Respectful, Topic, "and such."** These are orthogonal dimensions combined together per-Interaction, not one linear pick.
-   **\[Discuss\]** **Axes should have real mechanical stakes, not just cosmetic flavor** — e.g. a Language-complexity or customs-knowledge Axis option should plausibly be gated by whether the Player Character's own build/Stats actually knows the local customs (Fallout/Disco Elysium-style skill-gated dialogue), not available to click regardless. Ties into a **new, not-yet-designed category of non-combat Stats** — dDd: "the Characters will have a bunch of Stats not related to fighting and killing" that feed how Personality comes across, for both NPCs and Player Characters. Needs its own Stats-section pass before this is buildable.
-   **\[Resolved, design\]** **The success criterion, in dDd's own words: "situational storytelling and surprise... If the engine is capable of surprising the Player by what the Player or others say... because of how they decided to build the Personality and approach it with the axes."** Surprise should be *earned* — emergent from the combination of how the Player built their own Character's Personality/Stats and which Axes they chose against a given NPC's pool/Personality — not randomness or "wacky" surprise.
-   **\[Resolved, design\]** **Organic relationship state, not a bolted-on special case.** Naturally solves the "NPC repeats the same information" concern raised earlier: an NPC can track that the same Topic/Tone keeps getting raised and respond with gradual, earned "annoyance" or other reaction shifts — a side effect of the Pool+Axes structure already existing, not new plumbing.
-   **\[Resolved, foundational\]** **Authoring-efficiency rationale — the actual reason this design is worth the complexity.** The Narrative is meant to have "lots of exclusive paths" (mutually-branching, lockout-style) which is normally "a nightmare to author and stage" by hand. The Axes+Pools engine reframes what authoring actually means: instead of hand-staging every specific path, the work becomes **"getting the Set together, the right Actors in place, and beats of the Script good"** — cast the scene, place the right NPCs with the right pools/Personalities, nail the key facts — and the engine handles the combinatorial flexibility of *how* a Player actually approaches it.
-   **\[Discuss\]** **Navigation** — how the Player moves between locations/scenes at the World scale (not the local tactical Map, which is explicitly about small-area Combat/sight-gating per the Map coordinate work above). Not yet designed; likely a location-graph or Scene-list structure rather than a bigger tactical grid, but needs its own conversation.
-   **\[Discuss\]** **Interaction authoring format** — what a single authored Interaction/Dialogue Pool entry actually looks like as data (fields, tagging scheme), concretely enough to write the first one. Natural next step once Axes are pinned down further.

## Stats

-   **A \[Resolved, built\]** **Life + the real Wounds model** (designed 2026-08-15, **built and verified in code 2026-08-16**). The field itself (plain 1/0 on the Character sheet) was already built — see Character Panel. `wounds` (x) now counts UP from 0 in [js/combat.js](../js/combat.js) (`applyWound()`), replacing the old depleting-pool version; `WOUNDS_CEILING`/`isDown`/`isObliterated` live in [js/utils.js](../js/utils.js). All BUILDS templates and `blankCharacter()` in [js/character.js](../js/character.js) now start `wounds: 0`. The real model:
    -   **Wounds count up, not down.** `x/y` — `x` is sustained Wounds, `y` is that specific character's personal threshold before they're **Down** and can no longer fight unaided (common/weak characters often sit at `y=2`) — `isDown()` in utils.js. **Built:** a Down character is still a valid target for continued damage or Execution, not auto-removed; every `wounds <= 0`/`> 0` "defeated" check across combat.js/dm.js/dmtest.js/map.js/techniques.js was replaced with the new `isObliterated()` (below), since that's the state that actually removes a target from play now.
    -   **10 is the absolute ceiling** for anyone — full obliteration, no coherent Body left, universal regardless of a character's own `y`. **Built** as `WOUNDS_CEILING = 10` in [js/utils.js](../js/utils.js), with `isObliterated()` (`wounds >= 10`) as the real "no longer a valid target" check — target chips, the Map, DM's "Clear the dead," and dmtest's alive-counts all gate on this now, not on Down.
    -   **`x` can exceed `y`** through extreme healing/support, past a character's own down-threshold and up toward the 10 ceiling — how far is governed by the new **Resilience** stat (see below), not a fixed amount. A veteran losing a limb and staying in the fight vs. a commoner keeling over from one solid hit are mechanically the same obliteration ceiling, different personal `y` and different Resilience buffer. **Built as a reframe, not a separate number** — see item G below: there's no extra multiplier, this is just the emergent effect of Resilience shaving every hit lighter (item G's job 2).
    -   **Obliteration ≠ erasure.** Even at `x=10`, there can be a remnant (a head, a hand) — enough left for Possession or Necromantic reanimation to work with. A qualitatively different, lesser state than what happened to Gom, whose Form actually vanished from Reality. (Narrative framing only — no remnant/reanimation mechanic built yet, Obliterated enemies are still fully removable via "Clear the dead.")
    -   **Execution**, a distinct resolution path: instead of grinding `x` up to `y` through normal damage, an Execution attack goes straight for Life. Trivial once a character is already Down: `x+1` and `Life -1`, bypassing the rest of the Wounds climb entirely. **Built** as `applyExecution()` in [js/combat.js](../js/combat.js) — any plain Attack (Fast/Strong/Focus) against a Down-but-not-Obliterated target auto-resolves as an Execution instead of normal damage math, skipping Block/Flow entirely (a downed target is defenseless): guaranteed +1 Wound, Life clamped to a floor of 0. Essence attacks against a Down target are *not* scoped into Execution — they still climb Wounds normally. Verified live via DM Test: a Stray Dog (`y=2`) went Down on the first hit (Flow-overwhelm landed 2 Wounds), then three more staged Attacks in the same round each logged "Already Down — Execution lands: +1 Wound, Life 0", and a later round crossed the ceiling ("+1 Wound, Life 0 — Obliterated!"), after which further attacks correctly read "No target — already Obliterated" and the enemy dropped off the Map/target lists.
    -   **Life=0 reframed:** not "no body," but "not self-sustaining." Molten Ones are Life=0 because Kulkrow actively sustains them; Living Stone have genuine independent awareness (Life=1). Disembodied Gom and the Dark Cloud (present-day Kulkrow) are anomaly Characters that only function mechanically *because* the Possession mechanic lets a bodiless thing act at all — being possessed *themselves* would be genuinely hard for those two specifically (unlike an ordinary Life=0 Molten One, which per the Experiments section already requires Possession to act). Worldbuilding note to hold onto: the 4 Shield Fragments are likely going to become their own Characters. (Narrative only — no code changed here.)
    -   **Roster HP bar fixed to match** (2026-08-16): the Party roster's health bar in [js/ledger.js](../js/ledger.js) used to read `wounds/woundsMax` directly, which was "% health remaining" under the old depleting model — now that `wounds` counts up, that same ratio would show an *empty* bar on a fully healthy character. Inverted to `1 - wounds/woundsMax`. Verified: a fresh 0/3 character renders a full, non-"low" bar.

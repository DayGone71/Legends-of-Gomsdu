## Architecture / Systemization (new, 2026-08-25 — the anchor for the next Code Session)

**Not a feature item — a process problem, named directly by dDd after it became visible during the 2026-08-24 session.** His own framing: development has been "hardcode every thing instead of using the systems" — e.g. 13 triggers for one ability, 5 competing spawn systems (the `spawnCharacter()` consolidation on 2026-08-24 was one real fix of this shape, not a one-off) — instead of building tight, reusable systems meant to work across mechanics interchangeably. **A concrete instance already on record**: the S/Attack Glyph verification, same session (see [CHANGELOG.md](CHANGELOG.md) 2026-08-24) — the first pass "confirmed" the feature by manually setting a test NPC's Mindeye directly, not by checking the Glyph was reachable through real gameplay. dDd's own catch: *"You Manually gave it to him, which means the Feature doesn't work. It can't be tested."* That's the pattern at small scale: writing one-off functions that force a mechanic's internal state to prove a test case, rather than exercising the real interchangeable systems a Player would actually go through — which proves nothing about whether the mechanic is genuinely reachable.

**The stated goal for verification going forward**: walk through simple gameplay scenarios (loading them from JSON, in the same spirit as the existing spreadsheet→JSON Character Templates pipeline — see [[project-roadmap-workflow]]) through the *real* systems, instead of writing bespoke functions that reach in and break/force one specific mechanic just to get a passing test.

**Why this matters beyond code quality, per dDd directly (2026-08-25): "I haven't been clued in to the Code, basically, just the surface, and that became evident yesterday."** He's been engaging at the feature/gameplay surface, not the implementation — and the hardcoded, duplicated, one-off-per-mechanic pattern is exactly what made the underlying system illegible to him, not just harder for Claude to reason about. Fixing this isn't only an engineering-elegance concern — it's what makes the codebase something dDd can actually see into, not just something that happens to work when Claude touches it.

**Not scoped for implementation yet** — no specific tooling, JSON scenario format, or refactor plan has been designed. This is flagged as the priority for the next Code Session, ahead of picking up any individual feature below, including AP/Behavior-Queue draining (still relevant, see Personality/Behaviors, but should likely be *built* using whatever tighter-system discipline comes out of this conversation, not before it).

**First concrete application, CC3-1 (2026-08-26): the Language/Glyph data.** A live conversation walked the Glyph architecture against what the Architecture/Systemization thread actually means, found real gaps, and confirmed direction on each:
-   **Glyph identity needs a validity audit** — what's still current vs. stale across the 39 entries in [gomsdu-glyphic-system.json](../language/gomsdu-glyphic-system.json). Not done yet, agreed as the next pass.
-   **Behavior and Variety belong in the Glyph JSON, not duplicated as JS constants.** `GLYPH_BEHAVIOR` ([js/behaviors.js](../js/behaviors.js)) and `GLYPH_VARIETY` ([js/information.js](../js/information.js)) are hand-kept lookup tables separate from the Glyph data — confirmed as exactly the anti-pattern this section is about, and the duplication already caused a real bug: `KULOG`/`KALAG` are confirmed swapped in `GLYPH_BEHAVIOR` (see HANDOFF.md), the JSON and the JS silently disagreeing. Direction: the JSON owns the *mapping* (which Glyph triggers which Behavior key; each Glyph's Variety), the JS keeps owning the *implementation*.
-   **Some Glyphs also work as Marks — rare, significant, and Era-gated.** A Glyph's shape never changes across Eras, but its valid *roles* do: a Glyph that's standalone-only in First Era can pick up an additional role (used as a Mark, folded into a Compound) once a later Era's grammar supports it. Needs an Era-gated roles field per Glyph, not one fixed role tag.
-   **Marks and Grammar Lines are both thinner than the JSON currently implies.** Only the Chevron is confirmed as a Mark so far. `grammar.markers` has 2 entries (`ownership-line`, `next-idea-line`) against at least 5 more Line types already in use in saved Compositions (`goto-2-line`, `wildcard-above-line`, `follow-2-line`, `yield-line`, `extract-line`) — none of those are in the system JSON yet.
-   **Expression/Paragraph composition structure doesn't exist as data anywhere.** [gomsdu-compositions.json](../language/gomsdu-compositions.json)'s own metadata says it outright: "not re-parsed into structured grid data yet." Still genuinely open — flagged as needing real work-through, not scoped yet.
-   **Target identification is a 3-tier system, and First Era only has the bottom tier.** Category-level Target Glyphs (`KROW`/`KRO` — any Living Stone, any Inert Stone) are all First Era needs, since nothing has individual identity yet. Number (Second Era, tied to Sound/Music, Crystal Beings) and Name (Third Era, meaning lost but Sound persists, pioneered by Mud People) are both later, personal-identifier layers on the same Target slot — expected to extend to Ideas eventually too. First Era's schema needs to leave room for this without building Number/Name now (Numbers stay explicitly on hold until Second Era).
-   **Clarified, not a gap**: `oc/oc-protocol.js` is Dev-Environment-only tooling, unrelated to any of the above — its own header already says so. The one non-Technique-mediated call in the actual game (`spawnYom()` in [js/scenes.js](../js/scenes.js)) is a necessary bootstrap exception, not evidence of a missing category.

Full conversation detail in [CHANGELOG.md](CHANGELOG.md)'s 2026-08-26 entry. No code touched — this was design/organization work, same as the Assessment that named this thread.

-   **I \[Discuss, 2nd Era\]** (added 2026-08-16) **Betrayal Attack + Hara Kiri** — two mechanics dDd designed live, watching the Ally Targeting System's Block-between-Allies edge case unfold (see [CHANGELOG.md](CHANGELOG.md) 2026-08-16), specifically because a plain boolean ("is this Ally-on-Ally") turns out to carry real narrative weight. Neither built yet, both well-specified enough to pick up directly:
    -   **Betrayal Attack**: attacking an Ally should never be "normal combat with the usual defenses" — General Block should **not** be able to intercept it at all, and the hit itself should bypass Flow entirely with a very high (dDd's example: 99%) Hit%. Per dDd, needs **no new button** — derived from context (an Attack staged with an Ally as target), though staging one probably deserves a confirmation warning. The one exception: a Technique that *helps* rather than hurts its Ally target (Embolden/Anchor, a future heal) is obviously not a Betrayal — needs some notion of "is this Technique beneficial or harmful," which doesn't exist as an explicit flag on `TECHNIQUES` yet.
    -   **Hara Kiri**: self-targeting (already possible via Combat's Ally Range and the DM Panel's Acting-As double-click) as a deliberate, narratively-loaded act — dDd's framing: "oh no, Torso is now False and Wounds X = Wounds Y!" — instant jump to the personal Down threshold plus a real per-Character Chunk flipping false. Blocked on the same per-Character 6-Chunk array already queued as a Character Templates prerequisite (see Party System item C below, also 2nd Era). **Tagged 2nd Era 2026-08-25, per dDd** — well-specified enough to pick up directly whenever that phase starts, just not now.
-   **J \[Discuss\]** (added 2026-08-16, CC5, from playthrough notes; precedent updated 2026-08-25) **Combat should let a Player act as their own Mini-Party members.** The original precedent this leaned on — "the same way the DM Panel already lets the DM act as any given Enemy" — is gone along with the DM Panel's removal (see Dungeon Master Panel section above). The real precedent going forward is Yom's own Direct Control (switch Active Character, take direct control of any Character) — the same general mechanism, not a DM-specific one, likely covers this need too. Statted Mini-Party members can already act and get swept into `resolveRound()`, but there's currently no way in the Combat Panel for a Player to switch context and stage actions *for* a specific Mini-Party member — only for themselves. dDd's own connection: this is where Party System item C's deferred solid/hollow Ally-vs-Mini-Party visual distinction (see `style-guide.md`) would start earning its keep, since a Player juggling their own Character plus multiple Mini-Party members needs to visually tell them apart while switching between them.
-   **K \[Discuss, foundational, confirmed direction 2026-08-25\]** (added 2026-08-23) **Encounters should be tied to locality, not the whole Map.** No longer "deliberately not started" — dDd's own confirmed framing, given while deciding to remove the DM Panel: "An Encounter isn't a Global World State, Time is. AP is how a Character can accomplish in that Time. Time works the same in or outside of Combat, Combat being local and ongoing with other Characters' Non-Combat Rounds." Encounter Start/End itself moves off the DM Panel entirely — initiated by the Player or another Character directly acting on the Player, not a DM-only button. There's already a real, non-DM path this can build on: the `S`/Attack Glyph Behavior (`CHANGELOG.md` 2026-08-24) already starts an Encounter without going through the DM Panel — it's just table-wide/coarse today, exactly the locality gap this item is about closing. Current state, checked directly against the code: `table.inEncounter` is one boolean on the whole table row, not per-Character or per-zone — `startEncounter()`/`endEncounter()` ([js/dm.js](../js/dm.js)) just flip it (and will need a new, non-DM-Panel home once that panel is removed), and there's exactly one dispatch point ([main.js](../js/main.js), the Resolve button) that runs either `resolveRound()` or `resolveNonCombatRound()` for literally everyone at the table at once. Starting a Combat Encounter anywhere currently drags every Character on the Map into Combat rules simultaneously, even one standing in an unrelated corner of a large Map.
    -   **The good news, already true**: the end-of-Round tick (Recovery, Attunement, Empower/Shadow-Link upkeep, Spill, Lava Tile-State) already runs unconditionally over every Player and Enemy regardless of which Resolve function fired — the underlying clock is already table-wide and decoupled from Combat/Non-Combat. A locality-based redesign wouldn't need to touch that part.
    -   **What would actually need to change**: `inEncounter` becoming something like a set of active zones (`{tiles, participantIds}`) instead of one flag, and the ~4 places that currently read it as a flat gate (Resolve's dispatch, `js/map.js`'s movement Combat/Non-Combat branch, `js/techniques.js`'s Technique-staging branch, `js/craftPopup.js`'s filtering) becoming "is *this* actor in an active zone" instead. Contained, not a full rearchitecture — but real.
    -   **A related, separate gap surfaced by the same check**: Combat has no staged Move action at all yet. `tryMoveActor()` ([js/map.js](../js/map.js)) is "the original, unchanged single-Tile instant move... Combat doesn't have its own Move action yet (still a separate future Mechanical Fix)" per its own comment — the one place left in the engine that still resolves instantly instead of staging-then-resolving. Locality-based Encounters would need this solved too, since a Character couldn't walk *out* of a fight without it.
    -   **The same zone concept extends to sync, not just rendering/gating — surfaced 2026-08-25 while discussing 50v50/100v100 scale.** dDd's own framing: a Player only needs their own Tile (or adjacent Tiles) rendered — everything elsewhere on the Map still happens, it's just not what the Battle Report/UI needs to show them. That's a render-scoping answer, but the deeper issue is sync: `sync.js`'s `mutateTable()` has exactly **one** `table._version` counter for the entire Table, so two causally-unrelated fights in different corners of the Map are forced to contend for the same optimistic-concurrency lock — more simultaneous local fights means more retry contention, independent of total Character count. The fix this points to: version (and realtime-subscribe) per zone, not per Table, mirroring `inEncounter`'s own `{tiles, participantIds}` redesign above. **Not scoped, not this Cycle — per dDd, expected to be Cycle 4's heavy focus, not Cycle 3's.**

    -   **\[2nd Era\]** (tagged 2026-08-25) **Mini-Tiles.** Every regular Tile is actually a 3x3 grid of 9 mini-tiles — this is why more than one Character can already share a Tile today; the game just doesn't model the mini-tile logic yet. Purpose: sense of scale, easier at-a-glance reads, and mechanics that only make real sense at sub-Tile resolution (Wall Formation, next bullet, is the first one). **Sub-coordinates are meant to be automatic, not manually tracked**: the Party Panel's Formation control decides where within a Tile each Character sits, and that sub-position holds steady across ordinary Tile-to-Tile movement — a Formation change moves it, plain Movement doesn't. **Exception**: an Enemy moving into an already-occupied Tile has to conform to whatever Formation is already established there, rather than picking its own sub-position freely.
    -   **\[2nd Era\]** (tagged 2026-08-25) **Wall Formation.** 3 Characters positioned across a Tile's width forms a real, geometric block — not an arbitrary threshold, an actual line of bodies filling the space (this replaces/grounds [js/map.js](../js/map.js)'s existing crowd-block heuristic, `ACTIVE_CROWD_THRESHOLD`, in real geometry once Mini-Tiles exist). dDd's own scale point: this holds at one Tile, but a real battle line easily strings several Tiles' worth of 3-vs-3 fronts together — "3 vs 3 with Tiles is really 15 vs 15 potentially" — so the mechanic, and whatever reads it, needs to hold up at that combined scale too, not just one Tile in isolation.
    -   **\[2nd Era\]** (tagged 2026-08-25) **Combat Sequencer display scoping (Sequencer Panel implication)**, to handle that scale. Instead of the Sequencer reading/animating every tick and blood-drop element globally across the whole Encounter, it should scope its *live display* to **the acting Character's own Tile** (dense fights) or **that Tile plus its neighbors** (calmer fights) — roughly "what the Character would actually notice, even out of the corner of their eye." The Ledger and Battle Report still log every single action regardless of display scope — this only trims what's rendered live, not what's recorded.
    -   **Scroll Bar.** Works at Tile granularity, not mini-tile — mini-tiles get no distinct visual indicator at all outside zoomed-in Mode, aside from Character Triangles (see Facing below) already being positioned correctly within their own Tile. Gets the **last row and last column reserved**, matching the Compass's existing dedicated-row/column treatment ([js/map.js](../js/map.js)'s `COL_OFFSET`/`ROW_OFFSET`) — that space stays reserved even when the scrollbar itself isn't currently needed/visible, not reclaimed by the Tile grid.
    -   **Variable Zoom — 3 levels (default, far out, close up). Kept current 2026-08-25, per dDd — not 2nd Era.** Worth flagging a real coupling though: this item's own description of close-up as "the natural zoom level where Mini-Tiles actually become visible/interactable" assumes Mini-Tiles exist, and that's now 2nd Era. Zoom is still worth designing/building now — just know close-up may end up a placeholder level (or need its own interim definition) until Mini-Tiles actually lands. Not yet decided which lever this actually pulls: shrinking/growing `TILE_SIZE` (same 7x7 footprint, different pixel scale) vs. changing how many Tiles are visible at once (`VIEWPORT_TILES`). Close-up is the natural zoom level where Mini-Tiles actually become visible/interactable; far-out is where they stay collapsed to Tile-only, matching the Scroll Bar note above.
    -   **7x7 viewport retrospective, per dDd.** The fixed 7x7 (see [CHANGELOG.md](CHANGELOG.md) 2026-08-20) was scoped for the Era 1 Scene specifically, and in practice "didn't feel as good as I was hoping" — but it did succeed at its two real goals: a static Map Panel, and dialing in Tile scaling for Regular View. ## Networking & Sync (new)

Surfaced 2026-08-17 by a real OC-caused failure (see [CHANGELOG.md](CHANGELOG.md) same date) — rapid sequential table mutations can clobber each other, since `mutateTable()` in [js/sync.js](../js/sync.js) resolves on network-write-landed, not on the realtime echo actually refreshing `AppState.table`, and `saveSession()` is a whole-row upsert with no version check. [oc/oc-protocol.js](../oc/oc-protocol.js)'s `ocMutate()` fixes this for OC's own call sequences (fetch fresh, mutate, save, update local state directly — no reliance on the echo). That is **not** a fix for the underlying architecture, just the self-inflicted OC case.

-   **\[Resolved, design\]** **Design Philosophy: ordinary gameplay mostly avoids this race by construction, not by accident.** dDd's framing, 2026-08-17: a human Player only ever writes their own Character/Mini-Party; the DM is the only actor whose actions touch everything else, and is unlikely to be racing anyone; and human click speed naturally paces writes far enough apart to round-trip before the next one fires. This downgrades the real-world urgency of the underlying race for human-vs-human play — it's why OC (capable of firing calls far faster than a human ever would) is the one actor that actually triggered it. Worth stating as an explicit design principle going forward, not just an informal hunch: **write scope stays narrow and per-actor by design**, which is most of why this hasn't bitten real play yet.
-   **\[Resolved\]** **The residual case: a real human-vs-human (or human-vs-DM) same-instant collision.** Fixed 2026-08-21 with real optimistic concurrency — see [CHANGELOG.md](CHANGELOG.md) same date for the full build/verification detail. `table._version` embedded in the existing `state` blob (no schema migration), a conditional write in `saveSession()`, and `mutateTable()` re-fetching and replaying the same mutation on a version conflict instead of silently losing either side's change. Verified against a real induced collision, not just reasoned about.
-   **\[Discuss, foundational, not chosen — 2026-08-21\]** **A queued/pulsed commit model — dDd's proposal, 2026-08-17, refined same day.** Given a direct choice between this and the smaller optimistic-concurrency fix above, dDd picked the smaller one — this remains a real, valid future direction (the *actual* architectural fix, only one writer ever performs the real commit) but isn't needed for the race that was actually reported, and still has the same open design questions below unresolved. Worth revisiting only if optimistic concurrency's own retry-and-replay approach ever proves insufficient in practice (e.g. genuine claim-contention over the same Tile/target, which replay-merge doesn't arbitrate — it was chosen because almost everything mutated in this codebase is additive/independent, not because contention can never happen). Instead of every client writing the shared state blob directly and immediately, actions get queued (as intents/commands) and nothing becomes canonical until a "pulse" drains the queue and commits everything at once — plus an out-of-band pulse whenever the DM does something drastic (Start Encounter, etc.). This is architecturally the *real* fix for the whole class of clobbering race (only one writer ever performs the actual commit), and it lines up with an already-established principle: "the Sequencer/Ledger should already have the information as soon as Resolve is hit... the 7 Second Sequence is basically for Human benefit" (dDd, see [CHANGELOG.md](CHANGELOG.md) 2026-08-16, Sequencer Panel) — real state changing at a discrete moment, with presentation riding on top, is already how Combat resolution works. **Shape settled 2026-08-17:**
    -   **The Pulse must never be visible to a Player as lag.** Per dDd: "The Pulse shouldn't impact the Player moving around and doing stuff. Everything should appear live to them." Own actions render instantly, locally (optimistic), same as today — the pulse is a reconciliation step behind the scenes, not a wait state.
    -   **Two non-conflicting edits (different Players/targets) don't need arbitration** — they both just land at the next pulse, no contest. **Genuine contention (two Players trying to claim the same thing — dDd's example: two people moving to the same Tile) gets resolved at pulse time by timestamp** — whoever's intent was queued first wins; the loser's action gets rejected. dDd's own framing for the visual: the already-planned Lava-pulse-on-the-Sequencer-circle effect can "bubble for a second" specifically when it has to actually arbitrate a real conflict, distinct from its normal quick flash on an uncontested pulse — giving the contested case a visibly different, slightly longer beat.
    -   **A rejected action needs to roll back with an explanation**, not fail silently — per dDd: "If something goes wrong (like the movement situation), they should get their action kicked back and a message that briefly explains why." Standard client-prediction/server-reconciliation shape: render optimistically, and if the pulse disagrees, revert the local render and surface a short reason (banner/toast, reusing the existing `showBannerError` pattern already used for movement-blocked feedback).
    -   **Who runs the pulse — open again as of 2026-08-25.** Originally "the DM's client, for now" (a real server-side function would be the durable, disconnect-proof version, "we aren't quite there yet"). With the DM Panel/TATA role retired (see Dungeon Master Panel section), there's no longer an obvious single privileged client to default to — table creator, whoever's playing Yom, or something else entirely needs a real answer whenever this item is picked up. Not urgent since the Pulse model itself is still unbuilt (optimistic concurrency covers the actual reported race today), but don't assume "the DM's client" still means anything.
    -   **Still open before this is buildable**: pulse cadence for lightweight, non-conflict-prone actions (does *every* action wait for a pulse, or only ones touching shared/contested state — chat and solo movement outside Combat currently feel instant and dDd's "never read as lag" rule suggests those may want to stay closer to today's direct-write model); the actual queue data structure and where it lives client-side before a pulse drains it; and how "drastic DM action ⇒ its own out-of-band pulse" interacts with a regular timed/triggered pulse cadence if one exists. Claude's honest read, given directly: DM-running-the-pulse removes the biggest unknown (no real backend function needed yet), which makes this meaningfully more buildable-soon than "far off" — but it's still a real, scoped change to the action-resolution model (queueing, per-target conflict checks, rollback+message UX), not a quick add-on. Worth its own dedicated session when picked up.

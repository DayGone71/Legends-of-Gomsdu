-   **\[Resolved\]** "Shield" turned out to be the existing Ally-crowding ring, not a missing feature — see [CHANGELOG.md](CHANGELOG.md)/[style-guide.md](style-guide.md) 2026-08-17.

Should sit alongside Attack/Block/Essence as a real Combat action surface, not a separate trip. The engine underneath (`openTechniqueUse`/`stageTechnique`) is already panel-agnostic, so this is mostly a UI-wiring job, not new mechanics. Was explicitly held until Character Templates (Stats/Party) resolved — that's now done, so this is unblocked.
-   **I \[Discuss\]** (added 2026-08-16) **Betrayal Attack + Hara Kiri** — two mechanics dDd designed live, watching the Ally Targeting System's Block-between-Allies edge case unfold (see [CHANGELOG.md](CHANGELOG.md) 2026-08-16), specifically because a plain boolean ("is this Ally-on-Ally") turns out to carry real narrative weight. Blocked on the same per-Character 6-Chunk array already queued as a Character Templates prerequisite (see Party System item C below).

Also surfaced a real gap in the Non-Combat Round as currently built: it strips AP out of Technique-staging entirely (`js/techniques.js`'s Non-Combat branch skips the `ap` cost on purpose, per dDd's original "doesn't scale to AP" framing for the Round overall) — but per this example, AP should still cap *how many actions* can be staged in one Non-Combat Round, same as Combat's `apSpent`/`ap` ceiling, just not consumed the fine-grained way Move's per-Tile AP is. Not reconciled — flagged for whenever Non-Combat's own AP model gets a real pass.

## Movement System

Also blocked on Stats' Control mechanics first, then comes before Party System — see the build-order note above. The base mechanic below is a real exception to that ordering — it got built directly rather than waiting on Control, so it's already live even though the section header's blocking note is still accurate for what's left.

-   **\[Discuss, foundational\]** (added 2026-08-22) **The Map Evolution — huge in scope, deliberately pushed off for now.** Per dDd: "It'll actually drastically alter what we have. The good news is that the shift is the intended final design, not a placeholder." **Facing (below) is the one piece of it dDd wants picked up first**, ahead of the rest of the Evolution. The sub-items below are dDd's own working notes on the rest of it, captured live before any of it goes to build — he's been thinking about Mini-Tiles specifically "since way before we started Dev," and is deliberately staging all of this to manage how much lands on Claude at once rather than dumping it all at once.
    -   **Mini-Tiles.** Every regular Tile is actually a 3x3 grid of 9 mini-tiles — this is why more than one Character can already share a Tile today; the game just doesn't model the mini-tile logic yet. Purpose: sense of scale, easier at-a-glance reads, and mechanics that only make real sense at sub-Tile resolution (Wall Formation, next bullet, is the first one). **Sub-coordinates are meant to be automatic, not manually tracked**: the Party Panel's Formation control decides where within a Tile each Character sits, and that sub-position holds steady across ordinary Tile-to-Tile movement — a Formation change moves it, plain Movement doesn't. **Exception**: an Enemy moving into an already-occupied Tile has to conform to whatever Formation is already established there, rather than picking its own sub-position freely.
    -   **Wall Formation.** 3 Characters positioned across a Tile's width forms a real, geometric block — not an arbitrary threshold, an actual line of bodies filling the space (this replaces/grounds [js/map.js](../js/map.js)'s existing crowd-block heuristic, `ACTIVE_CROWD_THRESHOLD`, in real geometry once Mini-Tiles exist). dDd's own scale point: this holds at one Tile, but a real battle line easily strings several Tiles' worth of 3-vs-3 fronts together — "3 vs 3 with Tiles is really 15 vs 15 potentially" — so the mechanic, and whatever reads it, needs to hold up at that combined scale too, not just one Tile in isolation.
    -   **Combat Sequencer display scoping (Sequencer Panel implication)**, to handle that scale. Instead of the Sequencer reading/animating every tick and blood-drop element globally across the whole Encounter, it should scope its *live display* to **the acting Character's own Tile** (dense fights) or **that Tile plus its neighbors** (calmer fights) — roughly "what the Character would actually notice, even out of the corner of their eye." The Ledger and Battle Report still log every single action regardless of display scope — this only trims what's rendered live, not what's recorded.
    -   **Scroll Bar.** Works at Tile granularity, not mini-tile — mini-tiles get no distinct visual indicator at all outside zoomed-in Mode, aside from Character Triangles (see Facing below) already being positioned correctly within their own Tile. Gets the **last row and last column reserved**, matching the Compass's existing dedicated-row/column treatment ([js/map.js](../js/map.js)'s `COL_OFFSET`/`ROW_OFFSET`) — that space stays reserved even when the scrollbar itself isn't currently needed/visible, not reclaimed by the Tile grid.
    -   **Variable Zoom — 3 levels (default, far out, close up).** Not yet decided which lever this actually pulls: shrinking/growing `TILE_SIZE` (same 7x7 footprint, different pixel scale) vs. changing how many Tiles are visible at once (`VIEWPORT_TILES`). Close-up is the natural zoom level where Mini-Tiles actually become visible/interactable; far-out is where they stay collapsed to Tile-only, matching the Scroll Bar note above.
    -   **7x7 viewport retrospective, per dDd.** The fixed 7x7 (see [CHANGELOG.md](CHANGELOG.md) 2026-08-20) was scoped for the Era 1 Scene specifically, and in practice "didn't feel as good as I was hoping" — but it did succeed at its two real goals: a static Map Panel, and dialing in Tile scaling for Regular View. Not a final call on viewport size once Zoom exists — worth revisiting alongside the Zoom work above, not assumed locked forever.
-   **\[Resolved\]** Facing (Party Facing control, Map Triangle rendering, Mini-Party propagation) — built and verified live 2026-08-22, see [CHANGELOG.md](CHANGELOG.md). **Directly unblocks Glyphs-to-Behavior below.**

## Networking & Sync (new)

Surfaced 2026-08-17 by a real OC-caused failure (see [CHANGELOG.md](CHANGELOG.md) same date) — rapid sequential table mutations can clobber each other, since `mutateTable()` in [js/sync.js](../js/sync.js) resolves on network-write-landed, not on the realtime echo actually refreshing `AppState.table`, and `saveSession()` is a whole-row upsert with no version check. [oc/oc-protocol.js](../oc/oc-protocol.js)'s `ocMutate()` fixes this for OC's own call sequences (fetch fresh, mutate, save, update local state directly — no reliance on the echo). That is **not** a fix for the underlying architecture, just the self-inflicted OC case.

-   **\[Resolved, design\]** **Design Philosophy: ordinary gameplay mostly avoids this race by construction, not by accident.** dDd's framing, 2026-08-17: a human Player only ever writes their own Character/Mini-Party; the DM is the only actor whose actions touch everything else, and is unlikely to be racing anyone; and human click speed naturally paces writes far enough apart to round-trip before the next one fires. This downgrades the real-world urgency of the underlying race for human-vs-human play — it's why OC (capable of firing calls far faster than a human ever would) is the one actor that actually triggered it. Worth stating as an explicit design principle going forward, not just an informal hunch: **write scope stays narrow and per-actor by design**, which is most of why this hasn't bitten real play yet.
-   **\[Resolved\]** **The residual case: a real human-vs-human (or human-vs-DM) same-instant collision.** Fixed 2026-08-21 with real optimistic concurrency — see [CHANGELOG.md](CHANGELOG.md) same date for the full build/verification detail. `table._version` embedded in the existing `state` blob (no schema migration), a conditional write in `saveSession()`, and `mutateTable()` re-fetching and replaying the same mutation on a version conflict instead of silently losing either side's change. Verified against a real induced collision, not just reasoned about.
-   **\[Discuss, foundational, not chosen — 2026-08-21\]** **A queued/pulsed commit model — dDd's proposal, 2026-08-17, refined same day.** Given a direct choice between this and the smaller optimistic-concurrency fix above, dDd picked the smaller one — this remains a real, valid future direction (the *actual* architectural fix, only one writer ever performs the real commit) but isn't needed for the race that was actually reported, and still has the same open design questions below unresolved. Worth revisiting only if optimistic concurrency's own retry-and-replay approach ever proves insufficient in practice (e.g. genuine claim-contention over the same Tile/target, which replay-merge doesn't arbitrate — it was chosen because almost everything mutated in this codebase is additive/independent, not because contention can never happen). Instead of every client writing the shared state blob directly and immediately, actions get queued (as intents/commands) and nothing becomes canonical until a "pulse" drains the queue and commits everything at once — plus an out-of-band pulse whenever the DM does something drastic (Start Encounter, etc.). This is architecturally the *real* fix for the whole class of clobbering race (only one writer ever performs the actual commit), and it lines up with an already-established principle: "the Sequencer/Ledger should already have the information as soon as Resolve is hit... the 7 Second Sequence is basically for Human benefit" (dDd, see [CHANGELOG.md](CHANGELOG.md) 2026-08-16, Sequencer Panel) — real state changing at a discrete moment, with presentation riding on top, is already how Combat resolution works. **Shape settled 2026-08-17:**
    -   **The Pulse must never be visible to a Player as lag.** Per dDd: "The Pulse shouldn't impact the Player moving around and doing stuff. Everything should appear live to them." Own actions render instantly, locally (optimistic), same as today — the pulse is a reconciliation step behind the scenes, not a wait state.
    -   **Two non-conflicting edits (different Players/targets) don't need arbitration** — they both just land at the next pulse, no contest. **Genuine contention (two Players trying to claim the same thing — dDd's example: two people moving to the same Tile) gets resolved at pulse time by timestamp** — whoever's intent was queued first wins; the loser's action gets rejected. dDd's own framing for the visual: the already-planned Lava-pulse-on-the-Sequencer-circle effect can "bubble for a second" specifically when it has to actually arbitrate a real conflict, distinct from its normal quick flash on an uncontested pulse — giving the contested case a visibly different, slightly longer beat.
    -   **A rejected action needs to roll back with an explanation**, not fail silently — per dDd: "If something goes wrong (like the movement situation), they should get their action kicked back and a message that briefly explains why." Standard client-prediction/server-reconciliation shape: render optimistically, and if the pulse disagrees, revert the local render and surface a short reason (banner/toast, reusing the existing `showBannerError` pattern already used for movement-blocked feedback).
    -   **Who runs the pulse: the DM's client, for now.** dDd's own call — a real server-side function (Postgres/edge function) would be the durable, disconnect-proof version, but "we aren't quite there yet." DM-runs-the-pulse is an accepted, explicit fallback for this stage of development, not a final architecture — the DM disconnecting mid-pulse is a known, accepted gap at this scope.
    -   **Still open before this is buildable**: pulse cadence for lightweight, non-conflict-prone actions (does *every* action wait for a pulse, or only ones touching shared/contested state — chat and solo movement outside Combat currently feel instant and dDd's "never read as lag" rule suggests those may want to stay closer to today's direct-write model); the actual queue data structure and where it lives client-side before a pulse drains it; and how "drastic DM action ⇒ its own out-of-band pulse" interacts with a regular timed/triggered pulse cadence if one exists. Claude's honest read, given directly: DM-running-the-pulse removes the biggest unknown (no real backend function needed yet), which makes this meaningfully more buildable-soon than "far off" — but it's still a real, scoped change to the action-resolution model (queueing, per-target conflict checks, rollback+message UX), not a quick add-on. Worth its own dedicated session when picked up.

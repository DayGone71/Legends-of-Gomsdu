### AP Draining via the Behavior Queue — Built, Broken Twice, Fixed Live

-   **The actual mechanism, per creator's own correction mid-build: the Behavior Queue is a fresh, from-scratch computation every Round, not something that persists and grows.** First attempt (an incremental per-Category push, one pick added per Round) was wrong — corrected to just reusing `fillBehaviorQueue()` (`js/behaviors.js`, already built and working from the 2026-08-24 Plan/Commit pass, untouched): every known Glyph across Movement/Actions/Targeting competes in **one combined pool** for up to 9 slots (cap tied to the Character's own AP), Repeat-penalty reset fresh on every computation, nothing carried over between Rounds. `resolveBehavior()` (`js/noncombat.js`) now drains from this same computation, 1 AP per dispatched Behavior, until AP or the Queue runs out.
-   **Root-caused, in order, three real problems found live before this actually worked:**
    1.  **The Player's own spawn never went through `spawnCharacter()` at all.** `js/scenes.js`'s `seedScene()` hand-rolled a second, parallel copy of "apply a Build's Stats/Personality/techniqueAccess/Mindeye onto a Character" (via `loadBuild()`/`makeActiveCharacter()` plus a manual field-copy pass) instead of reusing the one function every NPC and Yom already spawn through. Per creator: "You Spawn into a Character that is already prebuilt" — not a form to load and submit. Not a bug in the Queue itself; it's the same table-wide-flag limitation already named under Combat item K (Locality-based Encounters), now confirmed to interact directly with Auto Behavior. Not fixed today — flagged as the same already-scoped, bigger item.
    3.  **The actual bug: the Personality Panel's Queue display read stored table state that was only ever written *during* a Resolve.** For an AP-rich Character (fill and full-drain finish in the same click), that state is always `0` from the outside — the Queue was functioning correctly the whole time, it just had no live way to be *seen*.

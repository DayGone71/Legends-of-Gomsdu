### Interactions & Dialogue

Design conversation, no code yet. Fuller design space lives in [dialogue-system.md](dialogue-system.md). Foundational decisions settled this session:

-   **Combat is ~30% of the experience, not the core.** The other ~70% is World/Lore. Solo CRPG play is explicitly "super important" — core, not optional. DM-run play (this build's actual origin) is "the skeleton," not the only mode. Named influences: **KOTOR** for the experience, **Kenshi** for Progression.
-   **The game's founding design pillars, restated directly by dDd: "Power Asymmetry and access to Information. It's always been Social, as far as the Design."** Every system downstream should read as an expression of that pillar.
-   **Not "OC as DM."** The story isn't Claude improvising live as a game master. The game is heavily scripted via Interactions — clicking a Character, visiting a Town, any Dialogue Encounter — as the primary mechanism driving the story, pivotal-moment by pivotal-moment. Architecturally likely reuses the same data-driven, tagged-entry pattern already proven (Techniques, Possessor slots, Dialogue Pools).
-   **Dialogue content is pre-authored, not runtime-generated — "primarily, like Tier 5 Possessions."** Each NPC/Faction holds a fixed information pool, authored offline by OC during design conversations, stored as static game data. How a pool renders to the Player varies by the NPC's Personality.
-   **Runtime resolution is AI, not OC — no live API call during play.** OC's role is strictly authoring-time. At runtime, deterministic client-side logic (matching/filtering, same spirit as the Technique engine) selects what to surface from the pool.
-   **The Player's side of Dialogue is not a tree, not a wheel, and not free text.** Trees and wheels were rejected as "basically the same thing" (a single linear branching choice); free text rejected as too random without real NLU/a live API call. Instead the Player expresses approach via independent, selectable **Axes** — e.g. Tone, Language, Respectful, Topic, "and such" — combined per-Interaction, not one linear pick.
-   **The success criterion, in dDd's own words: "situational storytelling and surprise... If the engine is capable of surprising the Player by what the Player or others say... because of how they decided to build the Personality and approach it with the axes."** Surprise should be earned, not random or "wacky."
-   **Organic relationship state, not a bolted-on special case.** An NPC can track that the same Topic/Tone keeps getting raised and respond with earned "annoyance" — a side effect of the Pool+Axes structure already existing.
-   **Authoring-efficiency rationale.** The Narrative is meant to have "lots of exclusive paths" (normally a nightmare to hand-author). The Axes+Pools engine reframes authoring as **"getting the Set together, the right Actors in place, and beats of the Script good"** — the engine handles the combinatorial flexibility of *how* a Player approaches it.

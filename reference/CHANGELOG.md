    -   **Behavior and Variety belong in the Glyph JSON, not duplicated as JS constants.** `GLYPH_BEHAVIOR` (`js/behaviors.js`) and `GLYPH_VARIETY` (`js/information.js`) are hand-maintained lookup tables kept separately from the Glyph data — and that duplication already caused a real, live bug: `KULOG`/`KALAG` are confirmed swapped in `GLYPH_BEHAVIOR` (see HANDOFF.md), the JSON and the JS silently disagreeing. Needs an Era-gated roles field per Glyph, not a single fixed role tag.
    -   **Target identification is a 3-tier system, and First Era only has the bottom tier.** Category-level Target Glyphs (`KROW`/`KRO` — any Living Stone, any Inert Stone) are all First Era needs, since nothing has individual identity yet. Number (Second Era, tied to Sound/Music for Crystal Beings) and Name (Third Era, meaning lost but Sound persists, pioneered by Mud People) are both later, personal-identifier layers on the same Target slot — and the same tiering is expected to extend to Ideas eventually. First Era's schema needs to leave room for this without building Number/Name now.
    -   **Marks, Grammar Lines, and Expression/Paragraph structure are all thinner than the existing JSON implies.** Only one Mark confirmed (the Chevron); `grammar.markers` has 2 entries against at least 5 more Grammar-Line types already in use in saved Compositions; Expression/Paragraph composition rules aren't structured data anywhere — `gomsdu-compositions.json` is raw pasted Arranger text, by its own metadata "not re-parsed into structured grid data yet." A validity audit (what's still current vs. stale across the 39 Glyphs) is the agreed next pass, not done yet.
### AP Draining via the Behavior Queue — Built, Broken Twice, Fixed Live

-   **The actual mechanism, per creator's own correction mid-build: the Behavior Queue is a fresh, from-scratch computation every Round, not something that persists and grows.** First attempt (an incremental per-Category push, one pick added per Round) was wrong — corrected to just reusing `fillBehaviorQueue()` (`js/behaviors.js`, already built and working from the 2026-08-24 Plan/Commit pass, untouched): every known Glyph across Movement/Actions/Targeting competes in **one combined pool** for up to 9 slots (cap tied to the Character's own AP), Repeat-penalty reset fresh on every computation, nothing carried over between Rounds. `resolveBehavior()` (`js/noncombat.js`) now drains from this same computation, 1 AP per dispatched Behavior, until AP or the Queue runs out.
-   **Root-caused, in order, three real problems found live before this actually worked:**
    1.  **The Player's own spawn never went through `spawnCharacter()` at all.** `js/scenes.js`'s `seedScene()` hand-rolled a second, parallel copy of "apply a Build's Stats/Personality/techniqueAccess/Mindeye onto a Character" (via `loadBuild()`/`makeActiveCharacter()` plus a manual field-copy pass) instead of reusing the one function every NPC and Yom already spawn through. Per creator: "You Spawn into a Character that is already prebuilt" — not a form to load and submit. Fixed by replacing that whole duplicate path with a direct `spawnCharacter()` call, collapsing two sequential `mutateTable()` writes into one. Real, deliberate behavior change as a result: a Player's Scene-seeded Mindeye no longer capacity-checks per entry the way the old per-Glyph `deliverMindeyeEntry()` loop did — it's unbounded at spawn now, same as every NPC.
    2.  **`t.inEncounter` is one flag for the whole table.** Auto Behavior naturally drawing `S`/Attack (a real, normal pool candidate, nothing special) starts a real Combat Encounter, which halts `resolveNonCombatRound()` entirely — for everyone — until something ends it. Not a bug in the Queue itself; it's the same table-wide-flag limitation already named under Combat item K (Locality-based Encounters), now confirmed to interact directly with Auto Behavior. Not fixed today — flagged as the same already-scoped, bigger item.
    3.  **The actual bug: the Personality Panel's Queue display read stored table state that was only ever written *during* a Resolve.** For an AP-rich Character (fill and full-drain finish in the same click), that state is always `0` from the outside — the Queue was functioning correctly the whole time, it just had no live way to be *seen*. Per creator: "What is the point of designing a Gameplay interface for people to interact with using their eyes when you've built it so they can never see anything?" Fixed by making the display (`queueOf()`, `js/personality.js`) call `fillBehaviorQueue()` directly, live, on every render — same pattern the Panel's existing Likely/Runner-Up numbers already used. `resolveBehavior()` now computes its own local copy to drain from; nothing shared or stored between display and resolution.

No console errors at any point.

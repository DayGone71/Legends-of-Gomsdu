# Cycles

A **Cycle** is one Claude Code instance's full run — several Sessions (each a dated sitting of build/discuss work, logged in [CHANGELOG.md](CHANGELOG.md)) capped by an **Assessment**: a documentation-only pass that triages [ROADMAP.md](ROADMAP.md), reaffirms or re-prioritizes [ISSUES.md](ISSUES.md), and — the part that doesn't live anywhere else — captures what changed about *how the work itself gets done*, before the next Cycle's first Session picks up. Established 2026-08-25, dDd's own naming: "we've done 2 'runs'... Let's go with Cycles actually."

**Not the same axis as Era.** Era (First Era / Second Era / etc., see `ROADMAP.md`'s `[2nd Era]` tag) is a content/game-content phase — what's in scope to build right now vs. deliberately deferred. Cycle is a development-process phase — which Claude Code instance, how many Sessions, when the last triage pass happened. A single Cycle can (and currently does) span work all tagged the same Era — don't conflate "next Cycle" with "next Era" when reading either doc.

**Where each doc sits relative to a Cycle**: [HANDOFF.md](HANDOFF.md) is Session-level and ephemeral — written at the end of a Session for whoever picks it up next, overwritten each time, gone once superseded. [CHANGELOG.md](CHANGELOG.md) is Cycle-level and gets cleared, not accumulated — see its own header note: at the start of a new Cycle's first Session, it's wiped and starts fresh, since git's own commit history is the real permanent backstop, not a duplicate markdown archive. This file (`CYCLES.md`) is the one thing that's genuinely cumulative — written once per Cycle, at Assessment time, and never overwritten. If you want to know what happened inside the Cycle that's still current, read `CHANGELOG.md`. If you want to know what a whole *closed* Cycle accomplished and what changed about *process* because of it, read here — this is the only place that survives past the Cycle that produced it.
-   **A related workflow detail, per dDd, 2026-08-25**: Resolved items already move from `ROADMAP.md` into `CHANGELOG.md` at the start of a Session as routine housekeeping — not a special Assessment task. Clearing `CHANGELOG.md` for a new Cycle is the same kind of thing: normal Session-start work for that Cycle's first Session (e.g. CC3-1), not something an Assessment needs to do specially.

**A Cycle also gets a forward-looking Plan, set at the previous Cycle's Assessment — established 2026-08-25.** Per dDd: "We should have an actionable Plan for the Cycles... keep each Session clear focused." This is deliberately *not* something [VISION.md](VISION.md) should hold — VISION's whole value is being the rarely-touched constant; a Cycle Plan changes every Cycle by nature, and putting it there would just reintroduce the same drift that made VISION.md itself hard to read as of 2026-08-25 (bolted-on dated Addenda instead of a current, correct statement). Instead: VISION supplies the durable macro-order to draw from; the Cycle Plan here names the actual bounded slice of it (or a deliberate, named deviation from it — same pattern as the 2026-08-19 Wimbis pivot) that the upcoming Cycle is scoped to. Sessions inside a Cycle stay loose, not rigidly pre-assigned — the Plan isn't there to block a real mid-Cycle pivot, it's there to give a Session something to check a pivot against.

## How to run an Assessment

A checklist, not a script — dDd drives the actual decisions; this is what to walk through and in what order, plus the mistakes already made once so the next Assessment doesn't repeat them.

**1. Roadmap triage first.** Open with something like "what have you got?" and go through `ROADMAP.md`'s Discuss items one at a time. For each, land on one of: Ready, Deferred/Discuss (stays open), `[2nd Era]` (real but not now), or Delete (superseded/no longer wanted). Don't batch-decide — dDd answers per-item, often with backstory that changes the call (see `CHANGELOG.md`'s dated entries from this Assessment for the shape of that). Resolved items move into `CHANGELOG.md` as routine housekeeping, not a special Assessment step.

**2. Reaffirm `ISSUES.md`'s priority order.** Quick pass — does the ranking still hold, has anything new surfaced, has anything resolved.

**3. Full documentation review pass.** Don't just skim for typos — ask directly whether each doc is still correct, whether anything's missing, and whether docs that should reference each other actually do. This is where stale/superseded docs get found and cut (4 went this Assessment) and where a doc that's ballooned with historical narrative gets trimmed back to current-state rules (`scenes.md` 429→78 lines, `dialogue-system.md` 1130→408). **Watch for the failure mode already hit once**: proposing new structure (a `history/` folder, an archive scheme) to hold the material being cut, instead of just cutting it — git is the permanent backstop, docs don't need to duplicate it. If a cut feels risky, ask before deleting rather than guessing at a filename's intent (see the `gomsdu-dialogue-mechanics.md` vs `dialogue-system.md` near-miss, Cycle 2).

**4. JS comment cleanup, if the Cycle's produced enough narrative-comment drift to warrant it.** Not every Assessment needs this — it's a real code-editing task, not documentation-only, so confirm with dDd before starting. When it happens: one file at a time, strip dated "(2026-08-XX, per dDd)" quote-transcripts and historical correction narratives down to tight current-state statements, leave all logic untouched, verify each file live in the browser preview (reload, check console errors, exercise a real feature the file drives) before moving to the next. Report progress in small batches, not one giant silent pass.

**5. Set the next Cycle's Plan.** Pull the bounded next slice from `VISION.md`'s durable priority order — or name a deliberate deviation from it, same pattern as the 2026-08-19 Wimbis pivot, if that's what the Cycle's own learnings point to (Cycle 3's Plan opens with process/architecture work that has no slot in VISION's 1-9 sequence, for exactly that reason). Write it under a new `## Cycle N — Plan` heading here, above the current Cycle's own closing entry.

**6. Close the Cycle out.** Add the `## Cycle N — ended <date> (Assessment)` entry: Span (Session count/dates, full detail lives in `CHANGELOG.md`), then the real headline — process learnings, not feature recaps. What changed about *how work gets done*, matters more here than what got built. Naming a mistake and its fix belongs here too (see Cycle 2's Architecture/Systemization entry for the shape of that).

**7. Memory consolidation last, only once the Assessment's actual conversation is over.** Don't run it mid-Assessment because a wrap-up phrase sounded like a cue — confirm timing if unsure rather than guessing (see Cycle 2's own near-miss on this exact point).

**A note on altitude, since it's easy to lose while triaging**: `ROADMAP.md`/`ISSUES.md` decisions are Ready/Discuss/Deferred calls — fast, per-item. Doc rewrites are slower and worth pushing back on scope creep (smaller, tighter docs beat comprehensive ones — dDd's own correction mid-Cycle-2-Assessment: "there is simply too much information... we need a smaller scope"). Comments in code should describe current mechanics, not carry a change-log of who-said-what-when — that belongs in `CHANGELOG.md`/git, not inline.

## Cycle 2 — ended 2026-08-25 (Assessment)

**Span**: 6 Sessions — the first, CC2-1, on 2026-08-17 (the Session `VISION.md` was originally written in); the most recent ending 2026-08-24 (see [CHANGELOG.md](CHANGELOG.md) for the full dated record of what was built) — capped by this Assessment.

**Process learnings surfaced this Cycle — the Assessment's real headline, more consequential than any single feature:**
-   **Architecture / Systemization named as a real, standing problem.** Development had repeatedly hardcoded one-off logic per mechanic instead of building reusable, interchangeable systems (dDd's own examples: 13 triggers for one ability, 5 competing spawn systems), and verification had followed the same shape — bespoke functions forcing a mechanic's internal state open to fake a passing test, instead of walking a real scenario through the actual systems a Player would use. Concrete instance already on record: the 2026-08-24 S/Attack Glyph "verification" that manually set a test NPC's Mindeye rather than confirming the Glyph was reachable through real gameplay — dDd's own catch, live: "You Manually gave it to him, which means the Feature doesn't work. It can't be tested." See [ROADMAP.md](ROADMAP.md)'s new "Architecture / Systemization" section — it's now the explicit gate on Cycle 3's first Session, ahead of any individual feature.
-   **Why it matters beyond code quality, per dDd directly**: "I haven't been clued in to the Code, basically, just the surface, and that became evident yesterday." The hardcoded/duplicated pattern hadn't just made reasoning harder for Claude — it had made the actual implementation illegible to dDd himself, who's been engaging at the feature/gameplay surface throughout. The fix direction (JSON-authored scenarios run through real systems, echoing the existing spreadsheet→JSON Character Templates pipeline) is framed as restoring that legibility, not just tidiness.
-   **`[2nd Era]` tagging convention introduced into `ROADMAP.md`'s Legend** — orthogonal to Ready/Discuss/Deferred, explicitly separating "not a current priority" from "actively open." Applied to Betrayal Attack + Hara Kiri, the "Remove Party Member" button, the whole mini-Party system thread, and Mini-Tiles/Wall Formation (Variable Zoom deliberately kept current despite a real coupling to Mini-Tiles).
-   **"Assessment" formalized as its own session type**, distinct from a Code Session — documentation/triage only, no code touched. See [feedback_minimize_bloat_for_reasoning.md] / the project workflow memory (Claude's own memory system, not this repo) for the full standing definition.
-   **Combat Panel called as outdated, headed for a gradual teardown** — no new feature investment there going forward; the standalone popup is being wound down rather than extended, distinct from (and not blocking) the engine-level Locality-based-Encounters work that happens to be filed in the same ROADMAP section.

**Handed to Cycle 3**: the Architecture/Systemization thread (unscoped — no tooling or refactor plan decided yet, that's the actual first conversation), with AP/Behavior-Queue draining as the next concrete feature once that discipline exists to build it with.

# Issues

Bugs and glitches found in testing/playthroughs — distinct from `ROADMAP.md`'s `[Discuss]`/`[Ready]` design items. The dividing line: something you can point at and say "this broke, here's roughly when/how" goes here; an open design question ("needs another look," "needs a real conversation") stays in `ROADMAP.md`. Resolved-and-verified fixes for anything logged here move to [CHANGELOG.md](CHANGELOG.md) once closed, with a note left behind pointing to it.

Each entry: **Status** (Open / Investigating / Closed — unreproduced / Fixed), when found, when closed if applicable.

-   **Map-load race, residual — much rarer after the 2026-08-23 loading-gate/Seed fix (see CHANGELOG.md), but not gone. Root cause confirmed from reading js/sync.js, a hardening fix shipped 2026-08-23 (stale-echo guard's comparison baseline decoupled from mutateTable()'s own optimistic _version bump, which could get corrupted by a genuine write failure) — not yet re-confirmed live against the original symptom.** dDd ran a fresh load 5 times in a row: the Map-panel width stretch (the original symptom) only showed up once (the 4th run) instead of every time, but nearly every run still showed some *other* visible post-load change — "spawn ins," compass ruler numbers changing, Facing markers changing — after the load screen had already come down. The camera itself (which Tiles are in view) was correct every single run, which rules out `centerMapView()`/`AppState.mapViewOffset` — that part is genuinely fixed (it's local-only state, never touched by what's below).
    -   **Confirmed mechanism**: `mutateTable()` ([js/sync.js](../js/sync.js)) does NOT render anything itself — by design ("every render happens in response to a realtime update... keeps 'when do we re-render' consistent for everyone at once"). It mutates `AppState.table` in memory, `await`s `saveSession()` (the write landing), and returns — full stop. The actual re-render for that write fires later, whenever Supabase's realtime *echo* of it arrives back through `subscribeToSession()`'s callback (`js/sync.js`'s `connectToSession()`), a separate async event `mutateTable()` never waits on. `loadScene()`/`seedScene()` fire several sequential `mutateTable()` calls; `showLoading(false)` only waits for their local `await`s (the writes landing), not for each one's own realtime echo to come back and actually paint. Whichever echoes are still in flight when the gate closes each trigger their own `renderAll()` moments later, visibly on top of an already-shown Table — exactly "spawn ins"/compass-numbers/Facing changing after the screen looked done, and rare/order-dependent because it's racing real network round-trips.
    -   **Two real fix directions, not decided yet**: (a) the pragmatic one — hold the loading gate open slightly longer than the last `mutateTable()`'s own `await` (dDd's original "mandatory 1 second load screen" idea), cheap but timing-dependent, not a real fix if a echo is ever slower than the padding; (b) the correct one — make `mutateTable()` (or `loadScene()`/`seedScene()` specifically) actually wait for its own realtime echo to land before resolving, not just the write — more invasive, touches the core sync primitive every other `await mutateTable()` call site in the app relies on, needs real care/testing before shipping.
    -   **Mitigated, not fixed, 2026-08-24.** `seedScene()`'s own rewrite (see [CHANGELOG.md](CHANGELOG.md) same date, "`seedScene()` Collapsed to One Event") cut Scene genesis from up to 5 sequential `mutateTable()` calls down to 2 — fewer in-flight echoes for the gate to race against in the first place. Separately, the Loading Screen now fades out instead of cutting instantly, and Map tokens fade in rather than snapping into place (same date, "Scene-Genesis Reveal") — this doesn't close the underlying race (option (b) above is still unbuilt), but it makes the residual symptom read as an intentional part of the reveal instead of a visible glitch. Worth re-running dDd's original 5-fresh-loads test against the new build before deciding whether (b) is still worth doing.

-   **A UI issue "with sending Crafts via popup Menu" — reported 2026-08-23, not reproduced.** Per dDd, from solo playtesting: "It's obvious after sending, I think the actual description panel for the Technique is what is causing it, not when the popup itself appears." Investigated the whole panel-visibility chain (`openCraftPopup()` → `openTechniqueUse()` → `openPanel('technique-use')` → `stageTechnique()` → `closePanel()`) and drove the real click-handler flow three ways through the actual UI — self-target Channel, other-target Message on a Living Stone, and an immediate reopen on a second Target right after staging (checking for stale target/Glyph selections carrying over). `AppState.activePanel`, the backdrop, the craft-list popup, and the Technique Use panel's own content were all correct at every step, every time. Not reproduced doesn't mean not real — logged here so it isn't lost; if it recurs, a screen recording or a more precise "what does 'obvious' actually look like" would help a lot more than another blind pass.

-   **Toolbar buttons intermittently produce no visible change on click — found 2026-08-23, root cause not chased down, recurred twice on two different buttons.** First: "Create table" (fresh `read_page` ref each time, name field filled first) left the page on the same landing screen with `AppState.table` still `null` — no console error, no banner, no navigation. Second, same session, same symptom shape: the "Scripts" toolbar button — `read_page` after the click showed no new panel content, while calling `openPanel('scripts')` directly (bypassing the click) worked immediately. Both worked around by driving the underlying function directly instead of chasing it live, since neither was blocking the actual verification at hand. Possibly specific to the disclosed-testing harness's click timing rather than a real player-facing bug (both had worked earlier the same session on the identical flow) — flagged here rather than assumed fixed or dismissed, since it's now reproduced on two separate unrelated buttons.
    -   **A likely mechanism found, 2026-08-24, while testing the seedScene()/Yom rework.** Hit the exact same symptom a third time, on "Create table" again: a synthetic `computer` click landed at the correct on-screen coordinate (`document.elementFromPoint()` confirmed the right element every time) but never actually focused it — `document.activeElement` stayed `BODY` afterward, so a following `type` action had nothing to type into. This lines up with the Browser tool's own screenshot error seen earlier the same session ("the Browser pane is not displayed, so the page is not compositing frames") — a synthetic click may not produce real focus when the pane isn't actively composited. Calling the button's own `.click()` directly (bypassing the coordinate-based synthetic click entirely) worked every time as a reliable substitute. Strengthens, doesn't confirm, the existing "testing-harness artifact, not a real player-facing bug" theory — still worth a human eye if it's ever seen in normal play.

-   **A Player's own Tile falls back to the old letter-list instead of a Facing Triangle the moment they have a Mini-Party — found 2026-08-22, deliberately not fixed.** Any Mini-Party member shares their Player's Tile (no position of its own), so a Player with even one Mini-Party member always has 2+ occupants on their Tile — and per Facing's own scope cut (see [CHANGELOG.md](CHANGELOG.md) 2026-08-22), a Tile with more than one occupant renders the pre-existing comma-initial label, not a Triangle. **Confirmed acceptable by dDd for now**: real per-occupant Triangle positioning within a Tile needs the Mini-Tiles system (sub-Tile coordinates — see `ROADMAP.md`, Movement System's Map Evolution) to mean anything, so this isn't a bug to chase today. Logged here specifically so it gets picked back up **the day Mini-Tiles actually gets designed/built** — not before.

## Fixed

-   **Resolve-time Orders never confirmed in the Ledger — found and fixed 2026-08-23.** See [CHANGELOG.md](CHANGELOG.md) 2026-08-23, "Resolve-Time Orders Now Confirm in the Ledger."
-   **RO / OR's rotation was wrong in the Glyphic System data — found and fixed 2026-08-21.** dDd's report: editing the 4 Direction Glyphs (RO/OR, OP/PO, OK, KO) in [gomsdu-glyph-designer.html](../language/gomsdu-glyph-designer.html) to face the right way, "they kept overwriting each other" and he couldn't get all 4 correct. Checked the actual data: the shared `arrow` primitive's own description says "pointing up at rotation 0." OP/PO (180°, Down), KO (90°, Right), and OK (-90°, Left) were all internally consistent with that convention — but RO/OR (meant to be Up) was also set to -90°, an exact duplicate of OK's rotation rather than the 0° it needed. Fixed directly in [gomsdu-glyphic-system.json](../language/gomsdu-glyphic-system.json) (RO/OR's composition rotation: -90 → 0), a minimal one-value edit, not a re-serialize (an initial attempt via a full JSON.stringify round-trip reformatted unrelated array formatting throughout the file and was reverted before committing). **Working theory for the "kept overwriting" symptom, not confirmed with dDd**: the designer's File System Access handle (`fileHandle`) can't survive a page reload (a real browser security limit, not a bug) — if dDd was editing across multiple reloads without re-clicking "Connect File" each time, `saveGlyphBtn`'s handler would silently fall through to its download-a-copy fallback instead of writing the real file, and each of the 4 edits would layer onto the same stale in-memory snapshot rather than the previous edit — explaining why the file never ended up with all 4 correct. The status-text message discloses this ("...downloaded a new file — check your Downloads") but is easy to miss; flagged as worth hardening (a louder, unmissable warning) if this recurs.

-   **Mindeye's click-to-reveal did nothing — found and fixed 2026-08-21.** dDd's report: "I can't get Mindeye to open on my end. Clicking doesn't seem to do anything." **Real root cause**, confirmed via a genuine point-based hit-test (`document.elementFromPoint`, not a direct-dispatch-on-the-element test, which misleadingly "worked" and masked the bug at first): `.mindeye-gi-b` — the second GI twin, invisible (`opacity:0`) until the split animation — sits at the exact same center point as `.mindeye-gi-a` and paints after it in DOM order (same `z-index:2`), so it silently absorbs every click meant for `.mindeye-gi-a`'s own listener. GI-b never had a click handler at all, so the click landed on dead space. Fixed with `pointer-events:none` on `.mindeye-gi-b` in [css/panels.css](../css/panels.css) — it was never meant to be a click target in either state. Verified live via real hit-tested clicks (not direct element dispatch): the resting GI now correctly triggers the split, and the Glyph box correctly marks the entry seen and returns to the Gallery. Debug entries cleaned up after.

-   **Camera/scroll jumping to the top of the page after creating a Character (first Player/table creator only) — gone as of 2026-08-17, likely the same root cause as the entry below.** Found and logged as undiagnosed the same day; confirmed gone by dDd on a later check without a dedicated fix being made for it specifically — most likely already covered by the `overflow-anchor:none` fix below, which addresses the same general "wholesale DOM rebuild confuses the browser's scroll heuristics" mechanism. Re-open if it resurfaces somewhere the general fix doesn't reach.
-   **"Moving changes the camera in a bad way" / the view keeps reverting to the Party section.** Found 2026-08-17, dDd's playthrough note. **First attempt (same day) was insufficient** — preserving `#roster`'s own internal `scrollTop` in `renderRoster()` addressed a real but different bug (that one's real, see below); dDd confirmed live that the actual page-reverts-to-Party behavior persisted, "in a bunch of areas," not just after moving. **Real root cause, found on the second pass:** `renderAll()` in [js/main.js](../js/main.js) unconditionally rebuilds every major container's `innerHTML` (Ledger, Roster, Map, ...) on *every* table mutation, not just the piece that changed. Browsers' default scroll anchoring (`overflow-anchor:auto`) tries to keep the viewport visually stable when content shifts, but its heuristics get confused when the DOM nodes it anchored to are torn down and rebuilt wholesale rather than genuinely resized in place — a well-documented cause of exactly this "random scroll jump" symptom in apps that re-render this way, and it matches "a bunch of areas" since it's a page-wide rendering pattern, not one specific action. Fixed with `overflow-anchor:none` on `body` in [css/base.css](../css/base.css). **Confirmed by dDd on his own machine 2026-08-17** — "Objective 1 is working great!"
-   **Mini-Party add causes a Map/toolbar layout glitch — took three passes to actually root-cause, fixed for real 2026-08-17.** Originally found 2026-08-16, closed the next day as unreproduced, reopened 2026-08-17 after dDd hit it live ("gamebreaking... buttons are actually still usable, but they are behind the Map"). **Pass 1** (wrong): diagnosed as `.map-row`'s `flex-wrap:wrap` letting the right `.side-toolbar` wrap into an overlapping position below ~860px width — "fixed" with a stacked-column breakpoint. dDd correctly called this out on review as its own glitch, not a fix: "They should stay in their positions but shrink or whatever" (it also read badly on phone-sized screens). Also, his own `window.innerWidth` was 1357 — comfortably above the 860px breakpoint — so it never explained his persistent report at all; what he'd actually seen "during testing" was Claude's own browser resizing live while probing the bug. **Pass 2** (closer, still incomplete): removed the stacked breakpoint, tried making `.side-toolbar`/`.map-panel` genuine flex-shrink participants instead of wrapping — still overlapped at 700px, screenshotted live. **Pass 3 — actual root cause:** `#map-grid`'s inline `grid-template-columns` used bare `1fr` tracks, which default to `minmax(auto, 1fr)` — a CSS Grid column refuses to shrink below its own content's min-content width regardless of what its flex-box parent tries to allocate it. The grid was silently overflowing its allotted space and rendering at its natural size no matter what flexbox math said, which is what actually pushed it into the toolbar. Fixed at the source: `minmax(0, 1fr)` in [js/map.js](../js/map.js)'s `renderMap()`. **Landed alongside a bigger redesign dDd proposed mid-session** — the Map became the deliberately dominant, reactive element (`width:60%` of the row, `#map-grid` capped at `max-height:65vh` with internal scroll for overflow — "the most reactive thing to the page... use scrolling to support bigger sizes than the display") — while the side toolbars went back to a fixed, non-shrinking 148px ("more of a temporary thing... but they should definitely stay left and right"). See [CHANGELOG.md](CHANGELOG.md) 2026-08-17. Verified live via screenshot at both 700px and desktop width — clean at both, zero overlap, Map scrollbar visible at the narrow width. **Still not moved to a clean close** — per dDd's original "keep it open... just in case," and this one earned that caution twice over.
-   **Create-a-Character auto-opened on every reload, not just first join — fixed 2026-08-17.** Direct regression from the same day's original auto-open fix, which called `openPanel('character')` unconditionally from every `enterTable()` path, including a remembered-session rejoin. Fixed by gating it on the Player's own record actually having no `archetype` set yet (`blankCharacter()` defaults it to `''`) — see [CHANGELOG.md](CHANGELOG.md) 2026-08-17.
-   **TATA Veil Vision caused Party spacing to shift when toggled — root-caused and fixed 2026-08-17.** Real cause: `.roster-possessor`/`.roster-miniparty-member` rows had no explicit height, so a row's rendered height depended on whether it contained a `.roster-icon` span (16px font in a Possessor row) or just the empty-slot's plain `&nbsp;` text (11px) — real and "reserved empty" rows weren't actually the same size despite both being meant as fixed grid slots. Toggling Veil Vision flips Gom/Kulkrow between those two states, which shifted every Character's whole block height. Fixed with an explicit `height`/`line-height`/`flex` treatment in [css/panels.css](../css/panels.css) — verified live, roster-stack heights now pixel-identical before and after toggling. See [CHANGELOG.md](CHANGELOG.md) 2026-08-17.
-   **Player order in the Roster could shift after saving a Character sheet — fixed 2026-08-17.** dDd's report: "I could break it by joining and making my Character Sheet active. It would move me up one place in the Order." Cause: `saveCharacter()` in [js/character.js](../js/character.js) replaces `t.players[id]` wholesale from the sheet's fields — the newly-added `joinOrder` stamp (see same-day fix above) wasn't in that list, so every save silently reset it to `undefined`, which sorts first. Fixed by carrying `joinOrder` (and `departed`) forward the same way `possessors`/`miniParty`/`hitPercent` already were.
-   **Self highlight's accent bar got clipped on the left edge — fixed 2026-08-17.** dDd's screenshot showed the Green ring visibly cut off. Cause: the original CSS used a negative `margin-left` to pull the accent bar left of the row's own box, which can clip against a parent's edge depending on available padding. Replaced with an inset `box-shadow` in [css/panels.css](../css/panels.css), which by definition can never render outside the element's own border box — can't clip against anything.
-   **Ally-crowding "Shield" ring wasn't counting Mini-Party members — found and fixed 2026-08-17.** What looked like two separate miscommunications (a "Shield" indicator that didn't exist, then a built-but-unverifiable Tile marker) turned out to be one real bug: dDd's original playthrough note ("No square around Player square when Shield up") meant the existing Cyan Ally-crowding ring (`.edge-ally`) — "Ally Movement Blocking and Shield are the same thing." It wasn't showing because `tileOccupancy()` in [js/map.js](../js/map.js) only counted top-level Players toward the 3+ threshold, never Mini-Party members — a Tile with 1 Player + 2 Mini-Party (3 warm bodies) read as only 1 toward the count. Fixed by folding each positioned Player's own Mini-Party (excluding Possessed members, who already have their own separate position and would otherwise double-count) into `activeAllies`. The unrelated General-Block Tile marker built earlier the same day under the wrong theory was removed entirely — see [CHANGELOG.md](CHANGELOG.md) 2026-08-17.
